# 사내 인프라 정보

[공통 배포 문서](../README.md) · [배포 문서 홈](../../../README.md) · [Kubernetes 셋업](../README.md#클러스터)

사내 서버·네트워크·서비스·저장소·운영 위치의 관리 원본입니다.
작업 전에 이 문서를 읽고 필요한 주제의 원본을 확인합니다. 에이전트 전용 규칙은 [AGENTS.md](AGENTS.md)에 있습니다.

## 무엇을 어디에 기록하나요?

| 바뀐 정보·찾는 정보 | 관리 원본 | 함께 대조할 정보 |
| --- | --- | --- |
| 서버 추가·교체·퇴역, 노드명·IP·역할, OS·버전·사양·SSH | [서버·노드](servers.md) | 서비스 배치, VIP backend, 데이터 위치 |
| VIP·DNS·backend·방화벽·CNI·CIDR·TLS 연결 경로·인증서 SAN | [네트워크](network.md) | 서버 주소, 공개 서비스 URL, 인증서 |
| 서비스 URL·namespace·앱 배치·스토리지 연결·사내 업무 API | [서비스·업무 연동](services.md) | 네트워크, 서버, 앱 실행 입력 |
| 사내 Git·registry·APT·PyPI·Helm·artifact·미러 이름 | [저장소·미러](repositories.md) | 소비 앱의 빌드·배포 입력, 설치 절차 |
| checkout·env·인증서·kubeconfig·데이터·백업 위치·담당자 | [운영 위치·책임](operations.md) | 서비스 배치, 노드, 인증서·복구 절차 |
| 서버에서 아직 적용·확인해야 하는 작업 | [서버 적용 대기 작업](pending.md) | 각 작업 행의 원본 문서 |

각 값의 원본은 위 표에서 지정한 문서 하나이며 다른 문서에는 원본 링크를 둡니다.
앱 실행 설정의 원본은 해당 앱의 manifest·env·Helm values이며 이 폴더는 그 입력을 자동 변경하지 않습니다.
설치·조회·장애 대응 명령은 [공통 배포 문서](../README.md)와 앱별 문서에서 찾습니다.
각 원본 문서의 담당자는 따로 표시하지 않으면 `미확인`입니다.

## 작업 전 공통 전제

- 사내 서버 배포는 Kubernetes를 사용합니다. CP1은 관리 명령 실행 위치이며 앱 실행 노드는 별도 배치 입력으로 정합니다.
- 사내 서버는 승인된 미러 또는 반입 파일만 사용하며 외부 public 저장소에 직접 접속하지 않습니다.
- 파일 검사·렌더 성공은 실제 서버 적용·접속 성공을 뜻하지 않습니다. 노드 Ready와 앱·DNS·VIP·TLS 정상 동작도 따로 확인합니다.

## 기록 규칙

1. 항목마다 **현재 값·용도 / 확인 상태 / 설정 원본 또는 확인 근거 / 담당자 / 남은 확인**을 기록합니다. 공통 내용은 절 앞에 쓸 수 있고, 다른 항목은 행에 따로 표시합니다.
2. 확인 날짜·변경 경위·완료 기록·이전 값·완료된 계획은 본문에 누적하지 않고 Git 이력으로 추적합니다. 버전·인증서 만료일·보존 기간·데이터 예시와 현재 필요한 이전·복구·호환 절차는 유지합니다.
3. 현재 유효한 주소·노드·용도·연결 관계·전체 미러 목록은 정리·요약만으로 삭제하지 않습니다. 운영 상태가 불확실하면 값과 함께 재확인할 대상을 명시하고 정상 동작으로 단정하지 않습니다.
4. 정보가 충돌하면 확인 대상과 설정 원본 또는 확인 근거를 대조합니다. 해결되지 않으면 후보 값과 남은 확인을 해당 항목에 표시하고 추정으로 하나를 선택하지 않습니다.
5. 변경이 예정·미적용이면 현재 운영 상태와 적용 예정 값을 구분하고, 서버 작업이 필요하면 [서버 적용 대기 작업](pending.md)에 행을 추가합니다. 적용이 확인되면 원본의 현재 값을 교체하고 해당 행을 삭제합니다.
6. 새 주소·노드가 확인되면 용도와 연결 관계도 함께 갱신하고 위 표의 대조 정보를 확인합니다. 서버 IP와 VIP, 운영 서버와 시험 서버를 구분합니다. 같은 전체 표를 다른 문서에 복제하지 않습니다.
7. 비밀번호·토큰·개인키·kubeconfig 내용은 기록하지 않습니다. 보관 위치·Secret 이름·발급 절차처럼 운영에 필요한 참조만 적습니다.
8. 확인되지 않은 담당자·접속 정보는 `미확인`으로 둡니다.
9. 정보 기록 요청은 실제 서버 적용 요청이 아닙니다. 문서 수정과 서버 적용·접속 검증을 구분합니다.

### 확인 상태를 기록하는 방법

| 상태 | 의미 | 함께 기록할 정보 |
| --- | --- | --- |
| 사용자 확인 | 사용자가 명시적으로 알려 준 운영값 | 대상·운영값·남은 확인 |
| 서버 조회 | 실제 대상 서버·클러스터에서 관측한 값 | 대상·조회 명령·민감정보를 제외한 결과 요약. Ready·접속 여부처럼 변동하는 상태는 작업 전 재조회 |
| 저장소 선언 | manifest·env·Helm values·chart lock의 배포 입력 | 원본 경로·설정 키·운영 적용 여부 |
| 안내·예시 | 설치 절차의 기준값·예시 | 현재 안내 문서 경로·사용 조건. 운영 적용 여부는 별도 |
| 미확인·충돌 | 값이 없거나 근거가 충돌함 | 후보 값·추가로 확인할 대상·질문·확인 주체 |

### 새 정보 입력 양식

새 행·절을 추가할 때 다음 형식을 사용합니다. 기존 표의 열은 정보에 맞게 유지하되 같은 항목의 정보를 여러 곳에 복사하지 않습니다.

```markdown
| 항목·대상 | 현재 값·용도 | 확인 상태 | 설정 원본·확인 근거 | 담당자 | 남은 확인 |
| --- | --- | --- | --- | --- | --- |
| <서버·서비스·저장소 이름> | <주소·역할·위치> | <사용자 확인 등> | <명령·파일:설정 키 또는 확인한 내용> | 미확인 | <없음 또는 후속 확인> |
```

변경 내용을 전달할 때는 **대상 / 현재 값 / 적용 여부 / 설정 원본 또는 확인 근거 / 담당자**를 알려 주면 됩니다.
일부 정보만 주어져도 확인된 부분을 먼저 반영하고 부족한 정보는 해당 문서의 추가 확인 항목에 남깁니다.
