# Kubernetes 처음부터 배포까지

[배포 문서 홈](../../../README.md) · [현재 서버 현황](../infrastructure/cluster.md)

SSH와 기본 Linux 명령은 사용할 수 있지만 Kubernetes는 처음인 담당자를 위한 안내입니다.
목표는 OS가 설치된 서버를 준비하고, 사내 구성에 맞는 클러스터를 만든 뒤 필요한 앱에 접속하는 것입니다.
명령은 단계별로 실행하며 앞 단계의 성공 조건을 확인한 뒤 넘어갑니다.

## 현재 가이드의 준비 상태

- 현재 노드 구성은 2026-09-16 사용자 확인 기준 Control Plane 3대와 Worker 2대이며 모두 Ready입니다.
- OS·Kubernetes 버전·설치 도구·CNI는 아직 확인되지 않았습니다. **빈 서버 설치 명령은 확정 전**입니다.
  01장의 조회 결과로 기준을 채운 뒤 02~03장의 설치 명령·설정과 버전별 공식 근거를 보완해야 합니다.
- 04~07장은 저장소의 현재 배포 도구와 기존 상세 문서를 연결합니다. 실제 서버 기동·접속은 별도 검증 대상입니다.
- 현재 Ready인 서버에서 Kubernetes 초기화·재설치를 할 필요는 없습니다. 기존 클러스터 배포는 01장 확인 후 04장으로 이동합니다.

## 명령을 읽는 법

- **내 PC:** SSH 접속과 브라우저 확인. 외부 인터넷 반입 준비는 허용된 외부 환경에서 수행합니다.
- **CP1:** 현황의 첫 Control Plane에서 배포 계정으로 실행합니다. 저장소 명령은 checkout 루트에서 실행합니다.
- **모든 노드 / 특정 Worker:** 해당 서버에 SSH로 접속해 실행합니다. CP1에 만든 데이터 폴더가 Worker에 생기지는 않습니다.
- `read` 입력에는 실제 값만 넣습니다. 설명용 `<...>`를 그대로 붙여 넣지 않습니다. 새 터미널에서는 변수를 다시 입력합니다.
- `kubectl --context "$KUBE_CONTEXT"`는 대상 클러스터를 명시합니다. 현재 context를 쓰는 기존 도구는 04장의 대상 확인을 먼저 수행합니다.
- 조회·검사, 파일 준비, 클러스터 적용은 서로 다른 작업입니다. `git pull`이나 검사 통과만으로 앱이 배포되지는 않습니다.
- 서버 선택 checkout에서도 이 공통 가이드는 포함됩니다. 선택하지 않은 앱의 상세 문서는 없을 수 있으므로 04장의 checkout 안내로 필요한 앱 범위를 먼저 준비합니다.

## 문서 유지 기준

설치·배포 명령을 바꾸면 해당 앱의 상세 문서를 먼저 수정하고 이 안내의 순서와 완료 기준을 맞춥니다.
실제 주소·노드 현황은 현황 문서에서 관리합니다. 비밀번호·개인키·토큰·kubeconfig 내용은 문서에 넣지 않습니다.
과거 ExecPlan과 일회성 초기화 기록은 현재 설치 설명의 원본으로 사용하지 않습니다.

각 단계의 기록은 `수행일 / 대상 / 실행 위치 / 버전·커밋 / 결과 / 미해결 항목`으로 남깁니다.
정적 문서 검사, manifest 렌더, 실제 서버 검증을 구분합니다. 최종 재현 검증은 빈 검증용 서버에서 수행합니다.
