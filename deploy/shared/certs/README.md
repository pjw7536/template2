# 서버 인증서 관리

사이트별 인증서·개인키를 준비하고 공용 Traefik에 등록하는 안내입니다.
명령은 **CP1의 Bash 터미널에서 저장소 루트**를 기준으로 실행합니다.

## 필요한 절차 선택

| 현재 상태 | 따라갈 순서 |
| --- | --- |
| PFX/P7B와 CA 원본만 있음 | [원본 준비](01-prepare.md) → [추출·검증](02-extract.md) → [서버 적용](03-apply.md) |
| fullchain과 개인키가 이미 있음 | [파일 위치 확인](01-prepare.md#준비할-원본과-생성될-파일) → [사이트 선택](02-extract.md#1-1-작업할-사이트-선택) → [기존 파일 검증](02-extract.md#1-4-이미-추출한-파일-검증--추출을-생략했다면-실행) → [서버 적용](03-apply.md) |
| 운영 사이트의 인증서를 갱신함 | 새 파일 추출·검증 → [TLS Secret 갱신](03-apply.md#2-2-kubernetes-tls-secret에-등록-또는-갱신) → [실제 인증서 확인](03-apply.md#2-4-실제-제공되는-인증서-확인) |

Keycloak과 업무 도메인을 모두 처리한다면 사이트를 바꾸어 추출·적용을 각각 진행합니다.
코드 블록은 한 블록씩 실행하고, `(`로 시작하는 블록은 마지막 `)`까지 함께 실행합니다.
터미널을 다시 열면 각 절차의 사이트·경로 변수부터 설정합니다.

## 보관·적용 기준

- 인증서·개인키는 도메인별 폴더에, 공용 CA 원본은 `ca/`에 보관합니다.
- Git에는 이 폴더의 안내 문서·`.gitignore`·폴더 유지용 `.gitkeep`만 보관합니다. 실제 인증서·개인키는 제외합니다.
- 두 사이트의 결과 파일명은 `fullchain.crt`, `private.key`이며 도메인은 상위 폴더로 구분합니다.
- 검증을 통과한 인증서는 공용 `etch-sso/traefik-tls`에 등록합니다. 앱 namespace에는 복제하지 않습니다.
- Headlamp OIDC용 CA 신뢰 설정은 HTTPS 인증서 등록과 별도로 진행합니다.

파일 역할과 전체 배치는 [원본 준비](01-prepare.md), Headlamp 설치에 돌아갈 위치는
[Headlamp TLS 안내](../../headlamp/03_TLS.md)를 확인합니다.

## 진행 중 막혔을 때

| 표시된 오류 또는 상황 | 먼저 확인할 내용 |
| --- | --- |
| `No such file or directory` | 저장소 루트에서 실행했는지, 해당 사이트 파일 이름과 경로가 맞는지 확인합니다. |
| PFX 비밀번호 오류 | 선택한 도메인의 PFX 비밀번호인지 확인하고 1-3을 다시 실행합니다. |
| PFX를 읽을 때 `unsupported` | 1-3의 OpenSSL 3 `-legacy` 안내를 확인합니다. |
| 인증서 검증 실패 | 선택한 도메인, 인증서 유효기간, 함께 발급받은 CA 원본이 맞는지 확인합니다. |
| `cmp`에서 파일이 다르다고 표시됨 | 1단계라면 인증서와 개인키의 짝을, 2-4라면 실제 서버가 제공하는 인증서를 확인합니다. |
| `kubectl` 인증 또는 권한 오류 | 2-1에서 선택한 context와 해당 계정의 접근 권한을 확인합니다. |
| HTTPS 연결 실패 | DNS가 가리키는 서버, 443 포트 연결, 서비스·Ingress 배포 상태를 확인합니다. |

오류 표의 1단계는 [추출·검증](02-extract.md), 2단계는 [서버 적용](03-apply.md)의 단계 번호입니다.
