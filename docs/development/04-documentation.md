# 문서 작성과 유지보수

[개발 안내](README.md) · [문서 홈](../README.md)

새로운 개발자가 실행·이해·수정에 필요한 정보를 찾을 수 있게 문서를 관리합니다.
코드 동작과 다른 설명을 쓰지 않으며, 내부 경로를 나열하기 전에 목적과 동작을 설명합니다.

## 어디에 작성할지

| 내용 | 위치 |
| --- | --- |
| 처음 실행하는 절차·일상 작업 | `docs/getting-started/` |
| 전체 구조·데이터·외부 연동의 개념 | `docs/concepts/` |
| 소스 수정·검증·DB 적용 방법 | `docs/development/` |
| 설정·실제 경로·명령·미러 참고 | `docs/reference/` |
| 기능 목적·화면·권한·처리 흐름 | `docs/modules/` |
| API method·path·인증·입출력·오류·부작용 | `docs/api/` |
| 앱 소스의 실행·빌드 | `apps/<app>/README.md` |
| 서버 배포·운영·공통 인프라 | `deploy/<app>/`, `deploy/shared/` |
| 개발 PC 설정·mock·실행 상세 | `local/<app>/`, `local/README.md` |
| 현재 작업 규칙·검증 방법·진행 중 계획 | `docs/agent/` |

공통 실행 명령은 루트 Makefile에, 절차의 상세 원본은 소유 문서에 유지합니다.
다른 안내에서는 같은 계정·설정·명령 표를 복사하기보다 해당 문서로 연결합니다.
서버에 필요한 절차는 선택 checkout에 포함되는 `deploy` 안에 작성합니다.

## 설명의 기본 순서

1. 문서의 목적과 독자가 끝낸 뒤 할 수 있는 일을 설명합니다.
2. 필요한 개념을 짧게 소개하고 낯선 용어는 [용어 안내](../concepts/04-glossary.md)로 연결합니다.
3. 동작 흐름을 설명한 뒤 실제 코드 경로·설정 이름을 제공합니다.
4. 실행 절차에는 준비 조건·실행 위치·명령·기대 결과·실패 시 확인 위치를 적습니다.
5. 상위 안내와 다음 문서를 연결합니다. 제목과 파일명은 문서의 역할을 드러내도록 정합니다.

API 문서는 method·path·auth·query/body·response·error·side effect를 보존합니다.
기능 문서는 목적·권한·주요 상태·화면 흐름·운영 확인 사항·관련 코드 경로를 설명합니다.
사용자에게 보이는 route부터 API client/hook, endpoint, selector/service/model, DB·외부 연동까지 추적할 수 있어야 합니다.

외부 URL·토큰·인증값은 필요한 env 이름과 역할로 설명합니다. 실제 비밀값을 문서에 복제하지 않습니다.
승인된 서버 전용 artifact 예외는 [배포 지침](../../deploy/AGENTS.md)을 따릅니다.

## 문서를 옮기거나 나눌 때

같은 폴더에 Markdown 문서가 여러 개라면 일반 안내 문서의 파일명 앞에 읽는 순서를 나타내는
두 자리 번호를 붙입니다. 예: `01-setup.md`, `02-usage.md`.
`README.md`는 폴더의 시작점으로 먼저 읽으며, 자동 탐색·작업 규칙의 고정 진입점인
`AGENTS.md`·`SKILL.md`·`PLANS.md`와 진행 중 계획 파일은 기존 이름을 유지합니다.
기존 배포 안내처럼 하위 폴더의 환경설정까지 이어지는 단계 번호는 유지합니다.
같은 폴더에서는 번호를 중복하지 않으며, 선택해서 보는 참고 문서는 주요 절차 뒤에 배치합니다.

이동 전후 경로를 기록하고 상대 링크·이미지·제목 앵커·검사 도구의 경로 참조를 함께 갱신합니다.
새 문서는 해당 분류 README에서 연결하며, 긴 절차를 나누면 준비 조건과 앞뒤 단계를 연결합니다.
최신 코드가 기준이며, 완료된 계획·결정 이력·점검 결과를 별도 문서로 누적하지 않습니다.
진행 중 계획은 완료 시 필요한 설명을 현재 문서에 반영하고 제거합니다.
기존 설명을 교체할 때는 실제 코드·설정과 대조해 지원하는 경로·입력·명령만 남깁니다.

저장소 루트에서 다음 검사를 실행합니다.

```bash
make audit-docs
```

업무·callback API, 중첩 app 모델, 관리 명령, Web feature의 구현 색인·기능 안내와 환경변수·필수 진입점 검사가 통과해야 합니다.
문서를 이동했거나 제목을 바꿨다면 상대 파일·제목 앵커·이미지 링크도 별도로 확인합니다.
검사 도구를 수정했다면 `make audit-tools-test`도 실행합니다.
정적 검사가 통과해도 실제 서비스 기동·로그인·배포까지 검증한 것은 아닙니다.
