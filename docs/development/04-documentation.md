# 문서 작성과 유지보수

[개발 안내](README.md) · [문서 홈](../README.md)

새로운 개발자가 실행·이해·수정에 필요한 정보를 찾을 수 있게 문서를 관리합니다.
코드 동작과 다른 설명을 쓰지 않으며, 내부 경로를 나열하기 전에 목적과 동작을 설명합니다.

## 현재 상태를 설명하는 원칙

- 본문에는 현재 구성·동작·사용법·제약·남은 확인을 작성합니다.
- 확인 날짜·변경 경위·완료된 작업 기록·이전 값은 본문에 누적하지 않고 Git 이력으로 추적합니다.
- 저장소의 설정 원본과 실제 운영 적용 상태를 구분합니다. 확인되지 않은 상태는 확인할 대상을 명시하며 정상 동작으로 단정하지 않습니다.
- 현재 지원하는 호환 동작과 필요한 이전·복구 절차는 유지합니다. 이전 값은 해당 절차에 필요한 경우에만 설명합니다.
- 버전·인증서 만료일·보존 기간·API 및 데이터 예시의 날짜는 정보 자체의 의미이므로 유지합니다.

## 어디에 작성할지

| 내용 | 위치 |
| --- | --- |
| 처음 실행하는 절차·일상 작업 | `docs/getting-started/` |
| 전체 구조·데이터·외부 연동의 개념 | `docs/concepts/` |
| 소스 수정·검증·DB 적용 방법 | `docs/development/` |
| 설정·실제 경로·명령 참고와 소유 영역 연결 | `docs/reference/` |
| 기능 목적·화면·권한·처리 흐름 | `docs/modules/` |
| API method·path·인증·입출력·오류·부작용 | `docs/api/` |
| 앱 소스의 실행·빌드 | `apps/<app>/README.md` |
| 서버 배포·운영·공통 인프라 | `deploy/<app>/`, `deploy/shared/` |
| 사내 운영 정보의 진입점·분류·기록 규칙 | `deploy/shared/docs/infrastructure/README.md` |
| 서버·네트워크·서비스·저장소·운영 정보 | `deploy/shared/docs/infrastructure/`의 주제별 원본 |
| 공통 배포 절차 | `deploy/shared/docs/`의 `kubernetes/`·`ingress/`·`certificates/`·`operations/`·`configuration/`, 색인은 해당 폴더 README |
| 개발 PC 설정·mock·실행 상세 | `local/<app>/`, `local/README.md` |
| 현재 작업 규칙·검증 방법·진행 중 계획 | `docs/agent/` |

공통 실행 명령은 루트 Makefile에, 절차의 상세 원본은 소유 문서에 유지합니다.
다른 안내에서는 같은 계정·설정·명령 표를 복사하기보다 해당 문서로 연결합니다.
서버에 필요한 절차는 선택 checkout에 포함되는 `deploy` 안에 작성합니다.

사내 운영 정보는 [사내 인프라 정보](../../deploy/shared/docs/infrastructure/README.md)의 분류에 따라 주제별 원본에서 찾고 갱신합니다.
`servers.md`·`network.md`·`services.md`·`repositories.md`·`operations.md`가 각 정보를 소유합니다.
현재 값·용도·확인 상태·설정 원본 또는 확인 근거·담당자·남은 확인을 함께 유지합니다.
서버 주소와 연결 관계는 보존하고, 교체된 값과 확인 경위는 Git 이력으로 추적합니다.

## 소유권 중심 재구성 권고

문서를 모두 루트로 옮기기보다 원본을 소유 영역에 두고 `docs/README.md`를 전체 문서 지도로 사용합니다.
서버에서는 루트 `docs/` 없이 배포 문서만으로 작업할 수 있어야 합니다.

| 영역 | 권장 역할·향후 위치 |
| --- | --- |
| 루트 `docs/` | 저장소 공통 입문·개념·문서 지도·에이전트 지침 |
| `apps/<app>/` | 앱 실행·개발·기능·API 설명. Portal 상세 문서는 향후 `apps/portal/docs/`로 모으는 후보 |
| `deploy/<app>/`, `deploy/shared/docs/` | 앱별 배포·운영과 공통 Kubernetes·사내 환경·미러 |
| `local/<app>/`, `local/README.md` | 외부 PC 설정·mock·개발 환경 실행 |

현재 루트 `docs/modules/`·`docs/api/`와 Portal 전용 개발·설정 설명은 기존 경로를 유지합니다.
이 권고는 이후 별도 문서 재배치 작업을 위한 것으로, 아직 존재하지 않는 경로를 현재 원본으로 안내하지 않습니다.

재배치한다면 Portal 전용 문서부터 내용의 실제 소유권을 분류하고 이동 전후 경로를 정합니다.
관련 README·AGENTS·스킬의 링크와 검사 도구의 고정 경로를 같은 작업에서 갱신합니다.
루트에는 공통 설명과 앱별 진입 링크를 남기고, 배포·개발 PC의 실행 절차는 각 소유 영역에 유지합니다.

## 설명의 기본 순서

1. 문서의 목적과 독자가 끝낸 뒤 할 수 있는 일을 설명합니다.
2. 필요한 개념을 짧게 소개하고 낯선 용어는 [용어 안내](../concepts/04-glossary.md)로 연결합니다.
3. 동작 흐름을 설명한 뒤 실제 코드 경로·설정 이름을 제공합니다.
4. 실행 절차에는 준비 조건·실행 위치·명령·기대 결과·실패 시 확인 위치를 적습니다.
5. 상위 안내와 다음 문서를 연결합니다. 제목과 파일명은 문서의 역할을 드러내도록 정합니다.

API 문서는 method·path·auth·query/body·response·error·side effect를 보존합니다.
기능 문서는 목적·권한·주요 상태·화면 흐름·운영 확인 사항·관련 코드 경로를 설명합니다.
사용자에게 보이는 route부터 API client/hook, endpoint, selector/service/model, DB·외부 연동까지 추적할 수 있어야 합니다.

외부 URL·토큰·인증값은 필요한 env 이름과 역할로 설명합니다. 실제 비밀값을 문서에 복제하지 않습니다.
승인된 서버 전용 artifact 예외는 [배포 지침](../../deploy/AGENTS.md)을 따릅니다.

## 문서를 옮기거나 나눌 때

앱별 배포 상세 절차는 `deploy/<app>/docs/`에 두고 `01-setup.md`, `02-environment.md`처럼
두 자리 번호와 역할 이름을 조합합니다. 앱별 준비·설정·인증·배포·운영 순서에 맞춰 연속 번호를 붙이고
참고 문서는 주요 절차 뒤에 배치합니다. 파일 번호와 README의 안내 순서를 함께 맞춥니다.
공통 절차는 `deploy/shared/docs/<주제>/`에 두고 `setup.md`, `operations.md`처럼 역할 이름을 유지합니다.
본문의 단계 번호는 각 문서 안의 실행 순서로 사용합니다.
공통 Ingress·인증서의 실행 원본과 파일은 `deploy/shared/ingress/`, `deploy/shared/certs/`에 유지합니다.
원본 옆 README에는 역할·입력·사용 조건과 상세 문서 링크를 둡니다.

루트 `docs/`의 기존 기능·API·입문 문서는 분류별 번호 관례를 유지합니다.
`README.md`는 폴더의 시작점이며 `AGENTS.md`·`SKILL.md`·`PLANS.md`와 진행 중 계획 파일은 고정 이름을 유지합니다.
이전 경로의 호환 안내는 보존 요청이 있을 때만 둡니다.

이동 전후 경로를 기록하고 상대 링크·이미지·제목 앵커·검사 도구의 경로 참조를 함께 갱신합니다.
새 문서는 해당 분류 README에서 연결하며, 긴 절차를 나누면 준비 조건과 앞뒤 단계를 연결합니다.
최신 코드가 기준이며, 완료된 계획·결정 이력·점검 결과를 별도 문서로 누적하지 않습니다.
진행 중 계획은 완료 시 필요한 설명을 현재 문서에 반영하고 제거합니다.
기존 설명을 교체할 때는 실제 코드·설정과 대조해 지원하는 경로·입력·명령만 남깁니다.

저장소 루트에서 다음 검사를 실행합니다.

```bash
make audit-docs
```

업무·callback API, 중첩 app 모델, 관리 명령, Web feature의 구현 색인·기능 안내와 환경변수·필수 진입점 검사가 통과해야 합니다.
문서를 이동했거나 제목을 바꿨다면 상대 파일·제목 앵커·이미지 링크도 별도로 확인합니다.
검사 도구를 수정했다면 `make audit-tools-test`도 실행합니다.
정적 검사가 통과해도 실제 서비스 기동·로그인·배포까지 검증한 것은 아닙니다.
