# Eval: Portal 작업 범위

## Task
같은 코드 상태의 별도 작업 공간에서 아래 요청을 각각 새 에이전트 세션에 전달한다.
시작 디렉터리는 apps/portal이다. 읽기 범위와 검증 선택은 에이전트가 판단하게 한다.

1. `Portal VOC 목록의 결과가 없을 때 안내 문구를 "등록된 문의가 없습니다."로 바꿔줘.`
2. `Portal VOC 목록 조회의 읽기 로직이 selector를 거치는지 점검하고, 위반이 있으면 기존 API 동작을 유지하면서 수정하고 검증해줘.`
3. `Portal 메일 sandbox 연동의 endpoint 계약을 바꾸려면 어떤 호출부·mock·env·검증을 함께 확인해야 하는지 조사해줘. 파일은 수정하지 마.`

## Success Criteria
- UI 요청은 Web 지침과 VOC feature부터 확인한다. 무관한 API·Airflow·설치형 제품 운영 문서를 읽지 않는다.
- API 요청은 API 지침과 VOC 도메인부터 확인한다. 발견된 의존은 공개 facade를 통해 추적하고 Django 검증은 Compose api를 사용한다.
- 외부 계약 요청은 관련 API 호출부에서 local 지침·스킬 및 필요한 env·mock·서비스 연결로 확장한다. 범위를 좁힌다는 이유로 mock을 누락하지 않는다.
- 적용하지 않는 모든 스킬·docs를 선독하지 않고, 전체 저장소 검색은 좁은 검색으로 해결되지 않을 때 이유를 설명하고 수행한다.
- 실제 변경에 맞는 검사를 선택하고, 읽지 않은 파일·실행하지 않은 검증을 완료했다고 보고하지 않는다.

## Measurement
- 변경 전후 같은 요청·시작 위치·모델·도구 설정으로 각각 비교한다.
- 초기 지침의 파일 목록·바이트 수, 읽은 고유 파일 수·읽기 횟수·영역 밖 읽기의 이유를 기록한다.
- 실제 세션 사용량을 얻을 수 있을 때만 토큰을 비교한다. 바이트 감소율을 토큰 절감률로 대체하지 않는다.

## Regression Notes
- 외부 계약을 놓쳤으면 필요한 확대 조건을 보완한다. 무관한 읽기가 많으면 첫 탐색 경로와 문서 연결을 보완한다.
- 새 세션 실측 없이 문서의 정적 경로 검토만 수행했다면 이를 구분해 기록한다.
