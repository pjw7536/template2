# ExecPlan: 등록 시 소속 입력과 접근 권한 분리

> 2026-09-25 후속 설계: [SDWT 하위 그룹 기반 공통 권한](keycloak-sdwt-group-authorization.md)을 확정했다.
> 아래 완료 표시는 Portal 내부의 소속·권한 분리 구현만 뜻한다. Keycloak 초기 등록·본인 SDWT user 가입,
> 그룹 권한 수신과 모든 앱의 공통 등급 전환은 후속 계획의 미완료 작업이다.

## 목표
- 기존 Portal 코드에서 소속과 접근 권한을 분리하고 최초 사용자 등록 시에만 SDWT를 입력한다.
- 소속 변경은 데이터 접근 권한을 자동으로 늘리지 않는다.

## 현재 상태
- Portal 등록 소속과 명시적 역할·앱별 데이터 범위를 분리했다.
- 일괄 등록 명령은 EPID·사번·Knox ID·SDWT CSV를 검증하고 신규 사용자만 생성한다.
- 로그인 시 소속 입력·재확인 화면을 제거하고 계정 화면은 등록 소속 조회로 변경했다.
- account migration 0007이 기존 소속 기반 권한과 부서 fallback 접근을 보존한다.

## 범위
- Portal 등록 서비스·관리 명령, 소속·권한 판정, 기존 화면, migration 및 회귀 테스트.
- Keycloak 확장·새 동기화 연동과 기존 Headlamp 변경은 포함하지 않는다.

## 설계
- 관리자가 참조테이블 내보내기 파일로 사용자를 사전 일괄 등록하고 SDWT도 함께 입력한다. EPID는 기존 avatarid 필드에 저장하고 로그인 연결은 기존 sabun 계약을 유지한다.
- 등록 완료 이후 사용자에게 소속을 반복 입력·확인하도록 요청하지 않는다.
- 이후 참조값으로 소속을 덮어쓰거나 참조 불일치 재확인을 요청하지 않는다.
- 사용자별 reference_sdwt 및 reference_sdwt_at_confirmation 필드는 추가하지 않는다.
- 소속 없음은 UserCurrentAffiliation 행을 만들지 않는다. 사용자의 확인 절차를 없앴으므로 미확인 상태를 별도 추가하지 않는다. 재등록은 기존 계정을 건너뛰므로 소속 없음도 유지한다.
- SDWT 조직 목록은 최신으로 관리하고 line은 적용 SDWT에서 도출한다. 독립 입력하지 않는다.
- Portal의 기존 소속 저장 구조를 사용한다. 별도 Keycloak 화면·확장·쓰기 연동은 추가하지 않는다.
- 기존 외부 스냅샷 API와 데이터는 유지하지만 갱신 시 사용자 재확인 플래그를 세우지 않는다. 신규 등록 입력은 별도의 참조 CSV로 받는다.
- 기존 소속의 암묵적 member와 앱별 현재 소속 데이터 범위를 명시적 권한으로 이관하여 보존한다. 소속 부서 fallback으로 얻은 앱 접근도 이관한다.

## 검증
- Docker Compose의 계정·인증 테스트 277건 통과. 최종 CSV 명령 테스트 추가와 migration 조정 후 등록·이관·개요 10건 재검증 통과.
- Django check 통과, makemigrations --check --dry-run에서 변경 없음.
- 프론트엔드 관련 Vitest 11건, 변경 JSX ESLint, production build 통과. 기존 큰 bundle 경고는 남아 있다.
- 환경·Makefile 회귀 테스트 36건, backend/frontend boundary 및 UI consistency 검사 통과.
- 로컬 검사 DB가 실행 중이지 않아 CI Compose에 기존 API 이미지·명시적 소스 마운트를 결합하고 별도 임시 PostgreSQL을 사용했다.
- git diff --check 통과. 운영 migration·실제 사용자 CSV 등록은 실행하지 않았다.

## 위험과 대응
- 소속 권한을 제거하기 전에 migration 0007을 포함해 배포해야 기존 접근이 유지된다. 배포 시 등록·권한 변경 작업과 겹치지 않게 운영한다.
- 기존 로그인은 sabun으로 연결되므로 참조 CSV에 EPID 외에 sabun·knox_id가 필요하다. 기존 사번 계약을 임의로 변경하지 않는다.
- 실제 파일은 제공되지 않았으므로 합성 CSV로 검증했다. 실제 운영 등록 전 dry-run이 필요하다.
- 기존 부서 identity 정책과 명시적 권한은 유지한다. SDWT·line을 권한으로 자동 해석하지 않는다.
- 초기 사용자 소속 없음은 허용한다. 이후 변경·정정용 새 기능은 이번 범위에 추가하지 않는다.
