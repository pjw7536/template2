# Etch Members

Keycloak의 소속(팀·라인·SDWT), 소속별 역할, 앱 역할을 관리하는 React 정적 웹입니다.
조직과 권한은 로그인한 플랫폼 관리자의 토큰으로 Keycloak Admin API를 직접 호출해 관리합니다. 업무 부하 탭은 별도의 IAM API와 SQLite 저장소를 사용합니다.
권한 데이터의 원본은 Keycloak이고, 변경 기록은 Keycloak 관리 이벤트에 실제 관리자 이름으로 남습니다.

## 기능

| 화면 | 할 수 있는 일 |
| --- | --- |
| 권한 | Portal 권한 매트릭스와 같은 형식. 행은 사용자, 열은 앱이며 셀에서 앱 역할을 바꿉니다. 이름을 누르면 소속·소속별 역할·세션 패널이 열립니다 |
| 조직 | 팀을 고르면 팀 → 라인 → SDWT 트리와 실제 소속 인원 수가 보이고, 라인 버튼으로 범위를 좁힙니다(여러 라인을 함께 켜고 끌 수 있고, `전체`는 선택을 해제합니다). 라인 노드를 누르면 라인 정보(하위 파트·전체 인원·직급별 인원), 파트(SDWT)를 누르면 파트 정보(전체 인원·직급별 인원·구성원)가 보입니다. 소속 구성원은 트리·상세의 이동 핸들을 다른 SDWT에 놓고 확인해 소속을 옮깁니다. 조직도 `편집`을 켜면 소속 변경·해제, 같은 팀 안의 라인 이동을 할 수 있습니다. 편집 중 SDWT 추가와 목록 CSV(`user_sdwt_prod,line_id,department`) 업로드는 모달에서 합니다 |
| 업무 부하 | 월별 라인 수치 입력, 공통 가중치 설정, 1인당 업무부하 비교 |
| 소속 업로드 | 사용자 소속 CSV(`userid,user_sdwt_prod`) 미리보기와 일괄 적용 |

화면은 너비별로 배치가 바뀌지 않는 고정 배치(최소 너비 1280px)이며, 창이 좁으면 가로 스크롤됩니다.

### 라인·파트 정보

라인 노드를 누르면 오른쪽에 소속 팀, 전체 인원, 직급별 인원, 하위 파트(SDWT) 목록과 각 파트 인원이 보입니다. 목록의 파트를 누르면 해당 파트 정보로 전환합니다. 파트 노드에서는 전체 인원·직급별 인원·소속 구성원을 확인하고 `편집`을 켜면 소속 수정 기능을 사용할 수 있습니다. 같은 노드를 다시 누르거나 상세 닫기를 누르면 패널을 닫습니다.

라인 노드 맨 아래에는 해당 라인의 `PL`, 각 파트(SDWT) 노드 맨 아래에는 해당 파트의 `파트장` 이름을 표시합니다. 대표 이름을 누르면 사용자 상세정보가 열립니다. 등록된 대표가 여러 명이면 모두 표시하며, 대표가 없으면 `미등록`, 조회 중이면 진행 상태, 조회 실패 시 `확인 불가`로 표시합니다. 가로형·세로형 모두 같은 기준을 사용합니다.

인원은 실제 SDWT 그룹 구성원을 사용자 ID로 중복 제거해 집계합니다. 직급은 인사 속성 `grdName`을 기준으로 하며, 빈 값은 `미등록`에 포함합니다. 구성원 조회 중이거나 실패하면 인원 수치를 확정해 표시하지 않습니다.

분임조·파트·SDWT는 같은 단위입니다. 라인 상세에는 실제 소속 구성원의 `job_title`을 기준으로 `PL`과 모든 하위 분임조의 `파트장` 목록을 표시하며, 파트장 이름 옆에 소속 분임조 이름을 함께 표시합니다. 파트 상세에는 해당 분임조의 `파트장`과 그 외 직책을 표시하며 PL을 파트 대표로 표시하지 않습니다. 대표 직책의 범위는 현재 소속 라인·SDWT를 따릅니다. 여러 명이 등록되어 있으면 모두 표시합니다. 이름을 누르면 사용자 상세가 열립니다. 해당 직책을 등록한 사람이 없으면 `미등록`으로 표시합니다. 권한 역할을 직책으로 해석하지 않습니다.

### 조직도 배치와 인원 펼침

조직도 도구의 `가로형`은 팀 아래 라인·분임조를 배치하고, `세로형`은 왼쪽부터 팀 → 라인 → 분임조 → 구성원 순서로 배치합니다. 기본 가로형은 계층 사이에 여유를 두고 표시합니다. 방향을 전환하면 인원 펼침 상태·선택한 상세는 유지하고 새 배치에 화면 맞춤을 한 번 실행합니다. 일반적인 노드 선택·인원 펼침·갱신으로 배율과 위치를 초기화하지 않습니다.

`Compact`는 인원 명단·대표자 이름·오른쪽 상세 패널을 숨기고 조직 노드와 실제 소속 인원 수만 표시합니다. Compact 가로형은 각 라인의 SDWT를 위아래로 쌓고, Compact 세로형은 SDWT를 좌우로 나열합니다. Compact 전환과 표시 영역·조직 크기 변경 때 화면에 맞춰 한 번에 전체를 표시합니다. 손 도구·확대·축소도 사용할 수 있으며, 끄면 이전 인원 펼침과 상세 선택을 복원합니다.

세로형에서 펼친 구성원 명단은 이름 카드를 위아래 두 줄로 나누고 좌우로 이어 표시합니다. 한 사람만 있으면 한 줄로 표시합니다. 인원이 많으면 손 도구나 확대·축소로 확인하며, 가로형은 구성원 명단을 위아래로 나열합니다. PL은 라인 노드, 파트장은 SDWT 노드에서 표시하므로 트리의 세부 구성원 명단에서는 제외하며, 실제 소속 인원·직급별 집계에는 포함합니다.

`인원 모두 펼치기`와 `모두 접기`는 현재 팀·라인 필터에 표시된 모든 SDWT의 구성원 목록을 열고 닫습니다. 상세 선택과 펼침 상태는 별도이므로 모두 접어도 선택한 상세 패널은 유지됩니다. 여러 SDWT 인원을 펼친 상태에서 다른 SDWT나 라인을 선택해도 나머지 목록은 유지하며, 선택한 SDWT를 다시 누르면 해당 목록과 상세를 닫습니다. 팀을 바꾸면 인원 펼침은 초기화합니다. 이 도구는 전체 화면에서도 사용할 수 있습니다.

### 조직도 확대·축소

조직도는 팀을 처음 열 때 트리 전체가 표시 영역에 들어오도록 배율을 맞춥니다. `−`·`+`로 배율을 조정하고 `100%`로 원래 크기, `화면 맞춤`으로 현재 트리 전체를 표시 영역에 맞춥니다. 일반 모드에서는 라인·SDWT 선택, 구성원 갱신, 창 크기 변경으로 배율을 자동으로 되돌리지 않습니다. 상세 영역과 알림도 트리의 폭·위치를 밀어내지 않습니다.

조직도 표시 영역은 가로·세로 스크롤바를 사용하지 않습니다. 구성원을 많이 펼쳐도 스크롤바 유무에 따라 조직도 폭이나 가로 중심이 바뀌지 않습니다.

`전체 보기`는 조직도 맵과 조작 버튼만 브라우저 전체 화면에 표시합니다. `전체 화면 종료` 또는 Esc로 돌아옵니다. 전체 화면에서도 사용자 상세와 소속 이동 확인창은 원래 크기로 열립니다.

`손 도구`가 기본으로 켜져 있으며, 조직도의 빈 공간을 끌어 화면을 이동합니다. 휠은 화면 이동에 사용하지 않고 포인터 위치를 기준으로 확대·축소합니다. `−`·`+` 버튼으로도 배율을 바꿀 수 있으며 Ctrl·Space 조합은 필요하지 않습니다. 구성원 이동 핸들을 끌면 기존처럼 소속 이동이 동작하고, 이름·라인·SDWT 버튼은 클릭 기능을 유지합니다.

손 도구는 조직도의 좌표를 직접 옮기므로 축소 상태나 화면에 맞는 작은 조직도도 상하좌우로 이동할 수 있습니다. `화면 맞춤`을 누르면 배율과 위치를 함께 초기화해 조직도를 표시 영역 안으로 되돌립니다.

### 구성원 소속 이동

기본은 보기 상태입니다. 조직도 도구 모음의 `편집` 토글을 켜면 이름 왼쪽에 이동 핸들이 나타나고, 트리와 오른쪽 상세 목록에서 소속을 이동할 수 있습니다. 편집을 끄면 핸들과 드래그·드롭 등록을 제거합니다. 보기에서도 구성원 전체 펼침·이름 상세·대표 표시는 유지되며, 토글로 배율·위치·펼침 상태를 초기화하지 않습니다. 팀을 바꾸면 보기 상태로 돌아갑니다.

1. 조직 탭에서 `편집`을 켜고 출발 SDWT를 눌러 구성원을 펼칩니다.
2. 트리 또는 오른쪽 상세에서 소속 구성원 이름 옆의 이동 핸들을 다른 SDWT 노드에 놓습니다. 펼치지 않은 SDWT·구성원이 없는 SDWT에도 놓을 수 있습니다.
3. 확인창에서 이동할 소속을 확인하고 `소속 이동`을 누릅니다. 취소하거나 같은 SDWT·노드 밖에 놓으면 변경하지 않습니다.

조직 탭의 트리·상세 목록과 팀·라인·SDWT별 인원 집계는 실제 SDWT 그룹 소속만 기준으로 합니다. 다른 소속이면서 역할만 직접 받은 사람은 목록과 집계에 포함하지 않습니다. 구성원은 이름순으로 정렬합니다. 직급은 인사 속성 `grdName`, 직책은 관리자가 입력하는 `job_title`이며 값이 없으면 `-`로 표시합니다. 트리에는 직책, 파트 상세 목록에는 직급·직책을 구분해 표시합니다. 소속별 역할 관리는 권한 탭의 사용자 패널에서 할 수 있습니다.

트리 또는 오른쪽 상세에서 구성원 이름을 누르면 사용자 상세정보 창이 열립니다. 이름·직급·EPID·로그인 ID·이메일·사번·사내 부서·원소속 부서와 실제 소속 팀·라인·분임조(파트·SDWT)를 표시하고, 보기 상태에서는 직책을 조회하고 편집 상태에서는 `직책`을 수정할 수 있습니다. 값이 없으면 `-`로 표시합니다. 이름 버튼은 Enter/Space로도 열 수 있고, 닫으면 누른 이름으로 초점이 돌아갑니다. 소속 이동은 이름 옆의 이동 핸들을 사용합니다.

직책은 `편집`을 켠 뒤 사용자 상세의 입력란에서 최대 80자로 입력하고 `직책 저장`을 누릅니다. `PL`·`파트장`을 제안하며 다른 직책도 입력할 수 있습니다. 비우고 저장하면 직책을 해제합니다. 저장 결과는 조직도·구성원 목록·직책별 담당자에 바로 반영됩니다. 화면을 연 뒤 다른 관리자가 직책을 바꿨으면 저장을 중단하므로 창을 닫고 다시 열어 확인합니다. 저장 중에는 창 닫기와 중복 저장을 막습니다.

직책은 [Keycloak User Profile](../../deploy/keycloak/k8s/claims/account-user-profile.json)의 단일 속성 `job_title`이며 관리자만 수정합니다. 사내 IdP에서 수신하거나 앱 토큰에 발급하지 않으며 로그인 때 덮어쓰지 않습니다. 직급·소속·권한 역할을 변경하지 않습니다. 프로필 반영 방법은 [User Profile 설정](../../deploy/keycloak/docs/02-configure.md#user-profile과-수신-mapper)을 따릅니다.

원소속 부서는 권한 탭에서 사용자 이름을 눌러 사용자 패널의 `원소속 부서`에 입력하고 `원소속 저장`으로 반영합니다. 빈 값으로 저장하면 기록을 지웁니다. SSO 부서는 `deptname`에 표시하며, 원소속 부서는 선택 속성 `original_deptname`으로 저장합니다. [User Profile 설정](../../deploy/keycloak/docs/02-configure.md#user-profile-권한)

한 번에 한 사람의 소속을 옮깁니다. 드래그 대상은 현재 트리에 표시된 팀·라인 범위입니다. 핸들을 클릭하거나 키보드로 초점을 맞추고 Enter/Space를 누르면 같은 이동창이 열리며, 다른 팀·라인도 선택할 수 있습니다. `편집` 토글이 켜져 있어야 합니다.

이동은 기존 소속 변경 규칙을 따릅니다. 직접 받은 소속별 역할·앱 역할은 유지하므로 이전 SDWT의 직접 관리자 역할이 자동으로 회수되지는 않습니다. 사내 부서와 다른 팀을 고르면 경고하고 `deptname`은 유지합니다.
저장 직전에 현재 소속을 확인해 화면을 연 뒤 다른 관리자가 먼저 옮긴 사용자는 변경하지 않습니다. 저장 중에는 중복 이동을 막으며, 실패하면 오류와 함께 구성원 목록을 다시 읽습니다. Keycloak 그룹·속성 변경은 여러 요청이므로 일부만 반영될 수 있으며, 실패 후에는 실제 소속을 확인해야 합니다.

드래그 인터페이스는 MIT 라이선스의 [dnd-kit React](https://github.com/clauderic/dnd-kit)를 사용합니다.

## 사용 조건

- [IAM 배포](../../deploy/iam/README.md)는 `iam` client, `/iam/platform-admins` 그룹, `org` client·관리 권한과 앱 역할 카탈로그를 반영합니다. 웹은 `/iam` 속성의 카탈로그에서 앱 열과 `org` client id를 읽습니다.
- `iam` 액세스 토큰에 `realm-management/manage-users` 역할이 있어야 사용할 수 있습니다. 관리자 그룹이 비어 있으면 [IAM 배포 입력](../../deploy/iam/README.md#입력)에 기존 계정의 EPID 한 개를 지정해 최초 관리자를 등록합니다.
- 사용자는 사내 로그인을 한 번 이상 해야 Keycloak에 존재하므로 검색·업로드 대상이 됩니다.

### 플랫폼 관리자 추가

1. 기존 관리자가 Etch Members의 **플랫폼 관리자** 탭을 엽니다.
2. 대상의 EPID를 입력하고 **계정 확인**을 누릅니다. 표시된 `display_name(loginid)`와 EPID를 확인한 뒤 **권한 부여**를 누릅니다.
3. 대상은 다시 로그인하면 Etch Members를 사용할 수 있습니다. 부여 시 Keycloak이 호출자의 관리 권한을 검사하고 그룹 가입을 관리 이벤트로 남깁니다.

## 권한 모델

권한은 세 가지로 나눕니다. 데이터 범위를 따로 두지 않고 소속별 역할로 정합니다.

| 구분 | Keycloak | 토큰 |
| --- | --- | --- |
| 소속 | 그룹 `/org/<팀>/<라인>/<SDWT>`. 한 사람당 SDWT 하나. 속성 `deptname`(팀 = 사내 부서)·`line_id`·`user_sdwt_prod` | `affiliation: {team, line, sdwt}` |
| 소속별 역할 | client `org` 역할 `sdwt:<SDWT>:<등급>`, 라인 전체 `team:<팀>:line:<라인>:<등급>`, 팀 전체 `team:<팀>:<등급>`(등급은 `viewer`·`user`·`admin`). 라인·팀 역할은 그 아래 SDWT 역할을 포함합니다. SDWT 그룹에 `sdwt:<SDWT>:user`가 연결되어 소속하면 자동으로 받습니다 | `org_roles` (펼쳐진 목록) |
| 앱 역할 | 앱 client 역할 `viewer` ⊂ `user` ⊂ `admin`. 기능이 여러 개인 앱(Portal)은 `<기능>:viewer`… 와 묶음 `all:viewer`·`all:user`·`all:admin` | `resource_access.<clientId>.roles` (그 앱 역할만) |
| 인프라 | 그룹 `/headlamp-admins` 등 | `groups` |

토큰 예시입니다(SDWT-C 소속, SDWT-C 관리자, SDWT-D 지원 조회).

```json
{
  "affiliation": { "team": "TEAM-1", "line": "LINE-1", "sdwt": "SDWT-C" },
  "org_roles": ["sdwt:SDWT-C:user", "sdwt:SDWT-C:admin", "sdwt:SDWT-D:viewer"],
  "resource_access": { "portal": { "roles": ["emails:viewer", "emails:user"] } }
}
```

`org_roles`에는 `sdwt:<SDWT>:<등급>` 값만 들어갑니다. 라인·팀 전체 역할을 받으면 그 아래 SDWT 역할로 펼쳐져 들어가고, 라인·팀 역할 이름은 토큰에 나가지 않습니다.
역할 이름은 모두 `종류:이름(:종류:이름):등급` 형식입니다. SDWT 역할에는 팀·라인을 넣지 않아 SDWT를 다른 라인으로 옮겨도 이름이 같습니다.

앱 역할을 받는 경로는 세 가지이며 모두 같은 claim에 합쳐집니다.

- 직접 부여: 매트릭스 셀
- SDWT 앱 역할: SDWT 그룹에 연결한 역할. 그 SDWT 소속 구성원 모두가 받습니다(지원 인원은 받지 않습니다).
- 기본 역할: 카탈로그에서 `open`인 앱·기능의 `viewer`. 모든 사용자가 자동으로 받습니다. `closed`는 부여받은 사람만 씁니다.

### 앱이 판단하는 방법

```text
앱 진입·SDWT와 무관한 기능 : 그 앱 역할의 가장 높은 단계
SDWT S의 데이터            : min(앱 역할, org_roles 중 sdwt:S:<등급>의 가장 높은 것). S 역할이 없으면 볼 수 없음
```

앱 관리자라도 `sdwt:SDWT-D:viewer`만 있으면 SDWT-D 데이터는 조회만 합니다. 여러 SDWT를 다뤄야 하면 그 SDWT 역할이나 라인·팀 전체 역할을 줍니다.

### 새 앱 추가

1. 앱 배포에서 Keycloak 로그인 client를 만듭니다. 토큰에 자기 역할만 들어가도록 `fullScopeAllowed=false`로 둡니다.
2. [카탈로그](../../deploy/keycloak/access/catalog.json)에 앱을 추가하고 [IAM 업데이트](../../deploy/iam/README.md#b-업데이트)를 실행합니다.
   역할·기본 역할이 만들어지고, 앱 client에 `affiliation`·`org_roles` scope가 연결되며, Etch Members 매트릭스에 열이 바로 나타납니다(웹 재배포 불필요).
3. 앱은 `resource_access.<clientId>.roles`와 `org_roles`로 위 규칙대로 판단합니다.

### 소속과 역할 변경 규칙

- 소속 변경: 이전 `/org` SDWT 그룹에서 빠지고 새 SDWT 그룹에 들어가며 `user_sdwt_prod`·`line_id` 속성이 바뀝니다. 소속별 역할은 그대로입니다.
- 팀은 사내 부서(`deptname`)와 같은 값입니다. `deptname`은 사내 로그인 때 인사 값으로 맞춰지며, Etch Members는 고른 SDWT의 팀이 사내 부서와 다르면 경고합니다.
- SDWT 추가: 팀·라인·SDWT 그룹, `sdwt:<SDWT>:<등급>` 역할 3개, 라인·팀 역할과 토큰 묶음 `org-all` 포함, SDWT 그룹의 `sdwt:<SDWT>:user` 연결을 한 번에 만듭니다(`make keycloak-org-sync`와 같은 결과).
- 라인 이동: SDWT 역할을 이전 라인 역할에서 빼고 새 라인 역할에 넣으며, 소속 구성원의 `line_id`를 바꿉니다.
- 이름에 `/`·`:`는 쓸 수 없습니다(`:`는 역할 이름 구분자). 같은 라인 이름이 여러 팀에 있을 수 있어 라인은 항상 `팀/라인`으로 구분하고, SDWT 이름은 전체에서 유일합니다.

## 권한 매트릭스

- 셀 점: 채운 색은 접근 가능, 테두리는 직접 부여, 테두리 없는 색은 SDWT 앱 역할·기본 역할·묶음 역할로 받은 권한입니다. `ADMIN`은 관리자입니다.
- 셀에서 바꾸는 것은 그 열의 직접 역할뿐입니다. `직접 부여 없음`을 골라도 SDWT 앱 역할·기본 역할·묶음 역할로 받은 권한은 남습니다.
- RBAC에는 개별 차단이 없습니다. 특정인을 막아야 하는 앱은 카탈로그에서 `closed`로 두고 필요한 사람에게만 줍니다.
- 인프라 열(Headlamp)은 클러스터 관리 권한이므로 변경 전에 확인 창이 뜹니다.
- 사용자 패널의 `세션 종료`는 모든 로그인 세션을 끊어 권한 회수를 즉시 반영합니다.

## 현재 앱 적용 상태

| 앱 | 권한을 읽는 곳 | 비고 |
| --- | --- | --- |
| Portal | 이전 역할(`portal-admin`, `portal-all-apps`, `<앱>-user`·`-admin`)과 `/portal-members` | 새 역할(`all:admin`, `emails:user` 등)로 전환 전까지 매트릭스 변경은 Portal에 반영되지 않습니다 |
| Airflow | 이전 역할(`Viewer`·`User`·`Admin`) | `apps/airflow/image/oidc_claims.py`를 `viewer`·`user`·`admin`으로 바꾸면 반영됩니다 |
| Headlamp | 그룹 `/headlamp-admins` | 매트릭스에서 바로 반영됩니다 |
| Grafana | 운영 모니터링과 업무 대시보드 조회 그룹 | 매트릭스에서 각각 부여·회수하며 Grafana가 로그인 시 조직을 동기화합니다. [운영 안내](../../deploy/monitoring/docs/02-operations.md#grafana-조직별-조회-권한) |

이전 역할은 `make keycloak-access-apply`가 경고만 하고 지우지 않습니다. 앱 전환 후 Keycloak에서 삭제합니다.

## 설정

런타임 설정은 `public/config.js`의 `window.__IAM_CONFIG__`(`keycloakUrl`, `realm`, `clientId`)입니다.
개발 기본값은 `http://localhost:8180`, realm `portal`, client `iam`입니다. 운영 배포는 IAM·Keycloak env의 공개 설정을 `config.js` ConfigMap으로 만들어 웹 컨테이너에 마운트합니다.

상단과 권한·조직 화면의 구성원 표기는 `display_name(loginid)` 형식입니다. 로그인 헤더는 ID Token, Access Token, UserInfo에서 확인한 표시 속성을 쓰고, 필요한 값이 비어 있으면 플랫폼 관리자의 자기 계정 프로필을 조회합니다. 하나만 있으면 그 값만 표시합니다. 구성원 상세의 이름, 로그인 ID, EPID는 각각의 필드에서 확인할 수 있습니다.

## 업무 부하

`업무 부하` 탭에서 기준월과 팀을 선택해 라인별 수치를 입력합니다. 첫 입력에는 Keycloak 소속 인원이 배치 인원의 기본값으로 들어가며, 저장한 인원은 해당 월의 기준으로 사용합니다.

- 기준월 말 담당 가동 설비 수와 월간 SPC·FDC Interlock, APC 가변, 설비 PM, Lot Hold 건수를 직접 입력합니다. 공정 난이도, 1인 평균 근무시간, 참고사항도 기록할 수 있습니다.
- 월 전체 클릭 수에는 기준월의 라인 인원 전체 업무 클릭 합계를, 월 전체 WF Move에는 해당 라인에서 생산된 WF의 기준월 Move 합계를 직접 입력합니다. 두 수치는 작업량 비교표에 표시하며, 미입력은 `—`로 표시합니다.
- SCI에는 기준월의 라인별 회사생활 만족도 점수를 직접 입력합니다. 소수와 0점을 입력할 수 있으며 공란은 미입력으로 표시됩니다. SCI는 라인 간 재배치 검토용 지표로 비교표에 표시합니다.
- 총 부하는 각 대수·건수에 가중치를 곱해 합한 값입니다. 1인당 업무부하는 총 부하를 기준 배치 인원으로 나눈 값입니다. 배치 인원이 0명이면 1인당 점수를 표시할 수 없습니다.
- 가중치는 기준월마다 저장해 그 달의 모든 팀과 라인에 공통 적용합니다. 초기 가중치는 담당 설비 2, SPC 1, FDC 1, APC 1, PM 3, Lot Hold 2이며 `가중치 설정`에서 변경할 수 있습니다.

## 개발 실행

업무 부하 탭을 실행할 때는 먼저 저장소 루트에서 업무 부하 API를 시작합니다.

```bash
python3 -m venv data/iam/.venv
data/iam/.venv/bin/pip install -r apps/iam/api/requirements.txt
IAM_WORKLOAD_PYTHON=data/iam/.venv/bin/python make iam-workload-dev
```

기본 개발 DB는 `data/iam/workload.sqlite3`입니다. `IAM_WORKLOAD_DB`로 경로를 지정할 수 있습니다. 다른 Keycloak을 사용할 때는 `IAM_KEYCLOAK_ISSUER`와 필요 시 `IAM_KEYCLOAK_CLIENT_ID`를 지정합니다. `IAM_WORKLOAD_PORT`를 변경하면 웹의 `IAM_WORKLOAD_API_TARGET`도 맞춥니다.

다른 터미널에서 웹을 실행합니다.

```bash
cd apps/iam/web
npm install
npm run dev          # http://localhost:5174
npm run test:run
npm run lint
npm run build
```

업무 부하 API 검사는 의존성을 설치한 Python으로 `python -m unittest discover -s apps/iam/api`를 실행합니다. 빌드한 웹을 별도로 호스팅할 때는 같은 출처의 `/api/workload/`를 `workload.application_from_env()` WSGI 앱에 연결하고, `IAM_WORKLOAD_DB`에는 영속 경로를 지정합니다.

개발 realm(`local/keycloak/k8s/realm-portal.json`)에는 `iam` client와 플랫폼 관리자 `90000004`가 들어 있습니다.
개발 Keycloak의 SDWT마다 더미 구성원 20명(SDWT 관리자 2명, 다음 SDWT 지원 조회 1명)과 라인·팀 전체 관리자를 채우려면 `make local-keycloak-dummy`, 지우려면 `make local-keycloak-dummy DUMMY_REMOVE=1`을 실행합니다(username `99`로 시작, 이메일 `@dummy.example.invalid`인 사용자만 다룹니다).
조직도 대규모 확인용 데이터는 다음 명령으로 준비합니다.

```bash
make local-keycloak-dummy DUMMY_LINES=12 DUMMY_TOTAL_USERS=2000
```

이 모드는 loopback 주소의 개발 `portal` realm에서만 실행합니다. 기존 팀에 라인을 균등 배분하고 라인당 SDWT를 4~5개로 맞춘 뒤, 지정한 전체 더미 인원을 균등 분배합니다. 팀 2개·라인 12개이면 SDWT 54개이며 2,000명은 SDWT당 37~38명입니다. 직급 4종과 라인마다 PL 1명·SDWT마다 파트장 1명을 채웁니다. 직급·직책 프로필 정의는 deploy의 공통 User Profile에서 필요한 항목만 등록합니다.

기존 일반 사용자와 소속 그룹은 보존합니다. 예약 EPID와 실제 사용자가 충돌하면 중단합니다. 기존 더미의 `/org` 소속은 하나로 맞추고 다른 그룹·직접 권한은 유지합니다. 같은 규모로 재실행해도 사용자를 중복 생성하지 않습니다. 자동으로 라인·SDWT·목표 범위 밖의 더미를 삭제하지 않으므로 규모를 줄이는 용도로는 사용하지 않습니다. 작업 후 실제 사용자 수·더미의 단일 소속·직책 수와 일반 사용자 속성·소속·직접 권한 보존을 조회해 검증합니다.

realm JSON에는 Portal 개발용 그룹(`/SDWT-A/…`)이 들어 있습니다. `/org` 소속 트리는 `make keycloak-sdwt-init` 또는 조직 탭의 SDWT 추가로 구성합니다. 개발 realm에 IAM 설정을 맞출 때는 개발 Keycloak 연결과 realm을 지정해 `make iam-keycloak-setup`을 실행하고, 확인한 계획은 `IAM_KEYCLOAK_APPLY=1`로 적용합니다.
